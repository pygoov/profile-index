# UV workspaces и общие библиотеки

## Суть проекта

Паттерн UV workspaces организует монорепозиторий как набор самостоятельных Python-проектов, которые могут использовать общие библиотеки и единые инженерные соглашения без объединения в один runtime. Каждый компонент сохраняет собственную проектную границу, а workspace-механизмы обеспечивают удобную локальную композицию, согласованное описание зависимостей и повторное использование платформенных пакетов.

Shared-library foundation отделяет общий код от прикладных сервисов. В неё могут входить небольшие библиотеки с минимальной публичной поверхностью, а также пакеты, которые централизуют инструменты разработки и не добавляют runtime-код. Такое разделение помогает отличать рабочие зависимости приложения от средств типизации, тестирования и статического анализа.

## Мой вклад

Владелец спроектировал независимый UV workspace pattern и основу общих библиотек как следующий этап развития монорепозитория. Он определил способ, при котором проекты остаются самостоятельно запускаемыми и при этом подключают локальные shared libraries через стандартные механизмы Python packaging. Также был сформирован подход к общему набору инструментов разработки через отдельный metadata-only пакет и dependency groups.

## Проявленные компетенции

Работа демонстрирует проектирование Python packaging, workspace-архитектуры и границ переиспользуемых библиотек. Существенным решением стало не просто объединение пакетов в одном репозитории, а сохранение независимости их жизненных циклов. Централизация применялась там, где она уменьшала расхождения в инженерных практиках, но не должна была скрывать зависимости или связывать запуск разных проектов.

## Архитектурная эволюция

UV workspaces стали продолжением более раннего этапа с custom DI и единым объектным графом. Центральная композиция хорошо выражала зависимости и координировала асинхронный lifecycle. Позднее архитектурный акцент был перенесён на автономность проектов, стандартные package metadata и явное подключение локальных библиотек. Это демонстрирует способность пересматривать уровень платформенной абстракции по мере изменения требований, сохраняя полезные принципы предыдущего решения.

Переход не обесценивает собственный DI-слой: он разделяет две разные задачи. Object graph отвечал за runtime-композицию, а workspace pattern — за организацию исходного кода, зависимостей и инструментов между независимыми проектами.

## Ключевые особенности

- самостоятельная работоспособность каждого проекта;
- локальные editable dependencies для общих библиотек;
- dependency groups для разделения runtime- и development-зависимостей;
- общий пакет инструментов без прикладного runtime-кода;
- явные границы shared libraries и их публичных интерфейсов.

## Технологический контекст

Python project metadata, UV, workspaces, dependency groups, editable installs и shared libraries.

## Перспективы развития

Подход допускает независимые политики фиксации зависимостей и выпуска, общие проверки совместимости и дальнейшее уточнение границ переиспользуемых библиотек.
