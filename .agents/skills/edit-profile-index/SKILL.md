# Редактирование Profile Index

Редактируй Markdown-портфолио без параллельной модели данных. Перед сообщением об успехе выполни всю процедуру проверки без кода.

## Когда использовать

Используй при добавлении, изменении, перемещении, переименовании или удалении карточек, каталогов проектов, навигации и документации портфолио.

Не используй для запросов только на чтение, изменения истории Git или изучения рабочего монорепозитория.

## Процедура

1. Прочитай корневой `AGENTS.md` и выполни `read-profile-index` для затронутого узла, цепочки предков и затронутого поддерева. Через `terminal` выполни только чтение Git: `git status --short --branch`. Готово, когда записаны исходные пути, начальное состояние и защищённая ранее существовавшая работа, включая untracked-файлы.
2. Определи правку относительными путями. Создавай каталог только для узла с собственной проектной идеей, вкладом владельца и проявленными компетенциями; иначе добавь раздел в родительскую карточку. Готово, когда у каждого создаваемого или сохраняемого каталога есть самостоятельная история.
3. Пиши карточку по единственному утверждённому шаблону и правилам из `projects/README.md`. Не добавляй YAML frontmatter или ID: идентичность задаёт путь. Готово, когда факты обоснованы, способ вклада указан точно, неизвестное опущено, а структура соответствует шаблону.
4. Обнови предков, если изменились их резюме или навигация по детям. При изменении смысла, пути или названия родителя рекурсивно проверь потомков. Готово, когда описания, размещение и ссылки согласованы во всём затронутом поддереве.
5. Обнови `competencies/README.md`, если изменилась представленность профессиональных компетенций или подтверждающие ссылки. Это синтез, а не список библиотек и не копия карточек. Для компетенции связывай подтверждающие проекты, когда они есть. Подтверждённый владельцем дополнительный опыт разрешено оставить явно не связанным с проектом; не удаляй его и не выдумывай проект ради ссылки. Готово, когда компетенции изменённых карточек отражены в синтезе, проектные ссылки разрешаются, а несвязанный опыт имеет явную корректную пометку.
6. Обнови `index.md`: каждый проектный узел должен быть указан ровно один раз в правильной иерархии; также должны быть ссылки на канонический и дочерние документы о компетенциях. Изменяй корневой `README.md` или `projects/README.md` только при изменении их отдельных обязанностей. Готово, когда навигация полна и не стала вторым реестром фактов.
7. Выполни все 19 пунктов раздела «Проверка после правки без кода» с помощью `read_file`, `search_files` и только read-only команд Git через `terminal`. Запиши фактические количества, просмотренные пути и нерешённые замечания. Не объявляй успех при пропущенном или непройденном пункте.

## Проверка после правки без кода

Не добавляй и не запускай скрипты, Python, схемы, генераторы, пакетные менеджеры, Make-цели, тесты, hooks или hosted CI. Используй нативные `read_file` и `search_files`; в `terminal` допустима только инспекция Git. Пункт пройден лишь при наличии указанного свидетельства.

1. **Исходная область.** Сравни сохранённое начальное состояние с итогом `git status --short --branch`. Пройдено, если каждая новая запись — утверждённая правка, а ранее существовавшая работа сохранена.
2. **Учёт изменённых путей.** Выполни `git diff --name-only`, `git diff --stat` и `git diff -- <утверждённые отслеживаемые пути>`; содержимое каждого утверждённого untracked-файла прочитай через `read_file`. Пройдено, если список изменённых файлов в точности согласован со status; обычный diff не считается проверкой untracked-файлов.
3. **Архитектура только на Markdown.** Получи инвентарь через `search_files(target='files')`. Пройдено, если содержимое портфолио и репозиторные skills представлены Markdown, не осталось ссылок на устаревшую исполнимую архитектуру и не добавлены Python, схемы, канонический JSON, генерируемый экспорт, пакетное окружение, Makefile-проверки или hosted CI; `.gitignore` допустим как служебный файл Git.
4. **Инструкции и skills.** Прочитай `AGENTS.md` и оба `.agents/skills/*/SKILL.md`. Пройдено, если корневые правила по одному разу направляют к ровно двум процедурам, отличают их от `competencies/`, а каждый skill начинается с `---` в первом байте, содержит только `name` и `description` в frontmatter, непустое тело и разделы о применении, процедуре, ошибках и проверке.
5. **Полнота каталогов проектов.** Получи файловый инвентарь `projects/` через `search_files(pattern='*', target='files')`, выведи уникальные родительские каталоги и запиши их число. Пройдено, если каждый каталог, включая `projects/`, содержит ровно один непосредственный `README.md`, а пустых содержательных узлов нет.
6. **Нет посторонних проектных файлов.** Проверь тот же инвентарь. Пройдено, если каждый файл под `projects/` называется `README.md`, а плоских черновиков и непроектных артефактов нет.
7. **Идентичность по пути.** Найди в проектных карточках YAML-разделители и поля ID через `search_files`, затем прочитай каждый кандидат. Пройдено, если нет frontmatter, `project_id` и параллельного идентификатора, а локальные ссылки относительны репозиторию.
8. **Полное покрытие индексом.** Прочитай `index.md`; через `search_files(pattern='README.md', target='files', path='projects')` получи список узлов. Разрешай ссылки индекса только относительно корня. Пройдено, если число README равно числу уникальных проектных ссылок, каждая карточка указана ровно один раз в иерархии каталогов и лишних проектных ссылок нет.
9. **Покрытие компетенций.** Прочитай `competencies/README.md`, дочерние документы, изменённые разделы «Проявленные компетенции» и все связанные карточки. Пройдено, если `index.md` ссылается на каждый документ о компетенциях, материальные компетенции изменённых карточек отражены в синтезе, каждая доступная подтверждающая ссылка разрешается, а дополнительный опыт без проекта явно отмечен как подтверждённый владельцем и несвязанный. Синтез не должен быть списком библиотек или копией карточек. Запиши числа документов, компетенций, проектных ссылок и явно несвязанных пунктов.
10. **Разрешение относительных ссылок.** Через `search_files` собери локальные Markdown-ссылки из корневого `README.md`, `projects/README.md`, `competencies/**/*.md`, `index.md` и карточек. Проверь каждую цель с точным регистром через `read_file` или `search_files(target='files')`. Пройдено, если все цели существуют и нет ссылок на устаревшую архитектуру.
11. **Структура карточек.** Прочитай каждую изменённую или перемещённую в изменённое поддерево карточку. Пройдено, если есть «Суть проекта», «Мой вклад» и «Проявленные компетенции», применимые необязательные разделы идут в утверждённом порядке, пустых разделов и заглушек нет.
12. **Рекурсивная согласованность.** Для каждого изменённого узла прочитай всех предков; при изменении смысла, заголовка или пути родителя найди и прочитай всех потомков. Пройдено, если резюме, размещение детей, эволюция и ссылки не противоречат друг другу; запиши числа предков и потомков.
13. **Нейтральность ко времени.** Найди через `search_files` маркеры текущей работы и обязательного roadmap, включая `сейчас`, `в настоящее время`, `работаю`, `поддерживаю`, `разрабатываю`, `планирую`, `будет`, `currently`, `now`, `maintain`, `developing`, `plan`, `roadmap`; прочитай каждый результат в контексте. Пройдено, если текст не подразумевает текущую занятость, сопровождение, активную разработку или обещанный план. Совпадение — кандидат на проверку, не автоматическая ошибка.
14. **Атрибуция вклада.** Прочитай каждый изменённый раздел «Мой вклад» и найди абсолютные формулировки, включая `полностью`, `единолично`, `весь код`, `solely`, `entire code`, `built everything`. Пройдено, если способ вклада указан явно, смешанное авторство сохранено, а утверждения не превышают подтверждённые факты.
15. **Проверка приватности.** Через `search_files` найди в Markdown URL, формы email, IPv4-подобные значения, абсолютные домашние и внутренние пути, слова об учётных данных, ключах и токенах, секретоподобные присваивания, обозначения организаций и заказчиков, даты, метрики и предоставленные владельцем запрещённые имена. Прочитай каждый результат в контексте. Пройдено, если технологии названы только как реализация и не раскрыты частные имена, реальные данные, адреса, payload, контакты, секреты, внутренние пути, указатели на источники, непроверенные даты, метрики, работодатели, клиенты или результаты.
16. **Нет выдуманных неизвестных.** Сопоставь каждое изменённое фактическое утверждение с допустимыми материалами назначения до правки и утверждёнными обезличенными временными отчётами. Не используй другие источники. Пройдено, если все утверждения поддержаны, а неизвестные организация, роль, дата, метрика, URL и результат опущены без догадки и заглушки.
17. **Разделение обязанностей документов.** Вместе прочитай корневой `README.md`, `projects/README.md`, `competencies/README.md` и `index.md`. Пройдено, если это соответственно точка входа, контракт дерева и карточки, канонический синтез компетенций и полная навигация — без дублирующего реестра фактов, списка библиотек, смешения с AI-процедурами и конфликтующей власти.
18. **Гигиена Markdown и diff.** Проверь изменённые Markdown-файлы на парные fences, финальный перевод строки, случайные инструкции шаблона, устаревшие заглушки и пути, маркеры конфликтов и хвостовые пробелы. Для отслеживаемых утверждённых путей выполни `git diff --check -- <пути>`; для каждого нового untracked-файла выполни `git diff --no-index --check /dev/null <путь>`, где код 1 означает ожидаемое различие, а код 2 — ошибку. Пройдено, если ручная и Git-проверки чисты.
19. **Финальная граница и ревью.** Зафиксируй `git status --short --branch`, снова посчитай изменённые пути и запроси независимое read-only ревью для широкой правки дерева. Пройдено, если числа согласуются с пунктами 1–2, защищённая работа и untracked-файлы сохранены, запрещённые файлы не читались, Git не изменялся и важных нерешённых замечаний нет.

В отчёте укажи фактически выведенные числа каталогов и README проектов, документов и синтезированных компетенций, ссылок компетенций на проекты, явно несвязанных пунктов опыта, уникальных проектных ссылок индекса, изменённых путей, просмотренных кандидатов приватности и нейтральности ко времени, непройденных пунктов и нерешённых замечаний. Не сообщай число без вывода соответствующего инструмента.

## Ограничения и типичные ошибки

- Не превращай `index.md` во второй реестр проектных фактов.
- Не помещай профессиональные компетенции в `.agents/skills/`, а AI-процедуры — в `competencies/`.
- Не сохраняй плоский черновик как каталог только потому, что черновик существует.
- Не добавляй в публичные карточки пустые заголовки, поля «неизвестно», ссылки на источники, реестры рисков, списки недостающих функций и служебные оговорки о проверке.
- Не переписывай смешанное авторство как единоличное.
- Не используй формулировки, подразумевающие текущую работу или обязательный roadmap.
- Не требуй проектную ссылку для корректно отмеченного дополнительного опыта и не создавай вымышленный проект для формального покрытия.
- Обычный `git diff` не показывает untracked-файлы; учитывай их отдельно и не изменяй без разрешения.
- Процедурная проверка не является исполнимым валидатором; для широкой правки запроси независимое read-only ревью.

## Проверка

- Все 19 пунктов пройдены, а требуемые фактические количества записаны.
- Каждый изменённый путь намерен; исходные изменённые и untracked-пути сохранены, если не входили в явную область правки.
- Каждый содержательный каталог проекта имеет один `README.md`, каждый узел ровно один раз указан в `index.md`, каждая относительная ссылка разрешается.
- Каждая изменённая карточка прошла проверку идеи, вклада, компетенций, нейтральности ко времени, атрибуции, приватности, рекурсивной согласованности и идентичности по пути.
- `git diff --check` и проверки новых файлов чисты, итоговый `git status --short --branch` записан, команды изменения Git не использовались.
